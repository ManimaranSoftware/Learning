## What is gRPC?

**gRPC (Google Remote Procedure Call)** is a **high-performance communication framework** used for communication between applications or microservices.

Instead of sending **JSON over HTTP** like a REST API, gRPC sends **binary data using Protocol Buffers (Protobuf)** over **HTTP/2**.

- Developed by **Google**.
- Uses **HTTP/2**.
- Uses **Protocol Buffers (Protobuf)** instead of JSON.
- Faster and more efficient than REST APIs.
- Commonly used for **microservices** and **service-to-service communication**.

## REST API vs gRPC

| Feature      | REST API              | gRPC                                                                       |
| ------------ | --------------------- | -------------------------------------------------------------------------- |
| Data Format  | JSON                  | Protocol Buffers (Binary)                                                  |
| Protocol     | HTTP/1.1 or HTTP/2    | HTTP/2                                                                     |
| Performance  | Good                  | Faster                                                                     |
| Payload Size | Larger                | Smaller                                                                    |
| Best For     | Client-to-Server APIs | Service-to-Service communication <br>(Communication between microservices) |

# HTTP/1.1 vs HTTP/2 – Short Notes

### HTTP/1.1

- Text-based protocol
    
- Usually uses multiple TCP connections for better parallelism
    
- No header compression
    
- Higher latency due to repeated headers and connection overhead
    
### HTTP and TCP
 - **HTTP** defines **what** data is exchanged (requests and responses).
- **TCP** ensures **how** that data is delivered reliably.

```
Browser
   │
HTTP/1.1 or HTTP/2
   │
TCP
   │
Internet
   │
Server
```
### HTTP/2

- Binary protocol
    
- Uses a single TCP connection
    
- Supports **multiplexing** (multiple requests/responses at the same time)
    
- Uses **HPACK** for header compression
    
- Supports **Server Push** (optional)
    
- Faster and more efficient than HTTP/1.1
    

---

## Multiplexing

**HTTP/1.1**

```
Request 1 → Response 1
Request 2 → Response 2
Request 3 → Response 3
```

**HTTP/2**

```
One TCP Connection
├── Request 1
├── Request 2
├── Request 3
Responses can be transferred concurrently.
```

**Interview line:**

> Multiplexing allows multiple HTTP requests and responses to share a single TCP connection simultaneously.

---

## HPACK (Header Compression)

### HTTP/1.1

Every request sends the same headers again.

```
Host: example.com
Authorization: Bearer xyz
Cookie: user=Manimaran
```

### HTTP/2

- First request sends full headers.
    
- Later requests send **references** to previously stored headers instead of repeating them.
    

**Purpose:** Reduce header size and improve performance.

**Interview line:**

> HPACK compresses repeated HTTP headers by storing them in a header table and sending references instead of the full header values.

---

| Feature    | HPACK                       | Gzip/Brotli                       |
| ---------- | --------------------------- | --------------------------------- |
| Compresses | **HTTP Headers**            | **HTTP Body (Payload)**           |
| Used in    | HTTP/2                      | HTTP/1.1 & HTTP/2                 |
| Purpose    | Reduce repeated header size | Reduce response/request body size |

### SOAP (Simple Object Access Protocol) – Short Notes

**Definition**

> SOAP is a **protocol** used for communication between applications. It exchanges data in **XML** format.

### Features

- Uses **XML** only
- Can work over **HTTP, HTTPS, SMTP, TCP**, etc.
- Strict standards
- More secure (supports **WS-Security**)
- Heavier and slower than REST because XML is verbose

# IL (Intermediate Language)

- CPU-independent intermediate code.
- Generated by the C# compiler.
- Stored inside assemblies (.dll / .exe).
- Converted into Native Machine Code by the JIT compiler.
**Native machine code** is the **binary instructions (0s and 1s)** that a specific CPU (Intel, AMD, ARM, etc.) can execute directly.

# Why C# Compiles to IL Instead of Native Machine Code

### Compilation Flow

```text
C# Code
   ↓
IL (Intermediate Language)
   ↓
CLR / CoreCLR
   ↓
JIT Compiler
   ↓
Native Machine Code
   ↓
CPU Executes
```

### Why not compile directly to machine code?

- Machine code is **platform-specific**.
    
- IL is **platform-independent**.
    
- The same IL can run on Windows, Linux, and macOS.
    

### Advantages of IL

- Platform independent
    
- Write once, run on multiple platforms
    
- JIT generates optimized machine code for the current CPU
    
- Supports runtime services like Garbage Collection, security, and exception handling
    

### What does JIT do?

> Converts IL into native machine code at runtime.

### Platform Example

```text
Same IL
   │
   ├── Windows CoreCLR → Windows Machine Code
   ├── Linux CoreCLR   → Linux Machine Code
   └── macOS CoreCLR   → macOS Machine Code
```

### .NET Framework vs .NET

- **.NET Framework** → CLR
    
- **.NET (Core/5/6/7/8/9)** → CoreCLR
    

Both execute:

```
IL → JIT → Native Machine Code
```

### Interview Answer

> C# is compiled into IL to make applications platform-independent. At runtime, the CLR/CoreCLR uses the JIT compiler to convert IL into optimized native machine code for the current operating system and CPU.

# AOT (Ahead-of-Time Compilation) – Short Notes

### What is AOT?

> **AOT (Ahead-of-Time Compilation)** converts **IL into native machine code before the application runs.**

### Compilation Flow

```text
C# Code
   ↓
IL
   ↓
AOT Compiler
   ↓
Native Machine Code
   ↓
CPU Executes
```

### JIT vs AOT

|JIT|AOT|
|---|---|
|Compiles at runtime|Compiles before runtime|
|Slower startup|Faster startup|
|More runtime flexibility|Less runtime overhead|
|Default in .NET|Optional in modern .NET|

### Advantages of AOT

- Faster application startup
    
- Lower memory usage
    
- No JIT compilation at runtime
    
- Good for cloud, microservices, containers, and mobile apps
    

### Interview Answer

> **AOT (Ahead-of-Time Compilation)** compiles IL into native machine code before execution, improving startup performance and reducing runtime overhead. In contrast, **JIT** compiles IL into native code at runtime.
---

# JIT (Just-In-Time Compiler)

- Converts IL into Native Machine Code.
- Executes at runtime.

### Types

- Normal JIT
	- Compiles methods when first executed.
	- Most commonly used.

- Pre-JIT
	- Compiles before execution.
	- Uses NGen or ReadyToRun.

- Econo JIT
	- Legacy implementation.
	- Optimized for low memory.

## Why do I sometimes see random characters?

Possible reasons:

- Gzip/Brotli compressed response
    
- Binary data (image, PDF, video, ZIP)
    
- HTTP/2 binary frames
    
- Encoded formats (Base64, Protocol Buffers, MessagePack)
    

---

## Performance vs Security

- Gzip/Brotli → **Performance**
    
- HPACK → **Performance**
    
- HTTP/2 Binary Frames → **Performance**
    
- Base64 → **Encoding only (not security)** 
    
- HTTPS (TLS) → **Security (encryption)**
    


|Technique|Purpose|
|---|---|
|**Gzip/Brotli Compression**|✅ Performance (smaller data, faster transfer)|
|**HTTP/2 Binary Frames**|✅ Performance (efficient protocol)|
|**Base64 Encoding**|❌ Not security. Just encoding for compatibility.|
|**Protocol Buffers / MessagePack**|✅ Performance (smaller and faster than JSON)|
|**HTTPS (TLS Encryption)**|✅ Security (protects data from attackers)|

# What happens when a .NET application starts?

1. User starts the application.
2. Operating System loads the executable (.exe).
3. .NET Runtime starts.
4. CLR is initialized.
5. CLR loads required assemblies.
6. Metadata is read.
7. IL is loaded into memory.
8. JIT Compiler converts IL into Native Machine Code.
9. CLR invokes the `Main()` method.

### For ASP.NET Core

10. Host is created.
11. Services are registered using Dependency Injection.
12. Middleware pipeline is built.
13. Kestrel Web Server starts.
14. Application begins listening for HTTP requests.

# How to stop an ASP.NET Core application

## Development

- Press **Ctrl + C**
- Sends SIGINT signal.
- Graceful shutdown begins.
- Active requests complete before application exits.

---

## Programmatically

Inject:

```csharp
IHostApplicationLifetime
```

Call:

```csharp
_lifetime.StopApplication();
```

---

## Production

### IIS

- Stop Website
- Stop Application Pool

### Linux (systemd)

```bash
sudo systemctl stop <service_name>
```

### Docker

```bash
docker stop <container_id>
```

### Azure / AWS

- Stop the App Service
- Stop the Container
- Stop the VM

---

## Configure Shutdown Timeout

Default: **30 seconds**

```csharp
builder.Host.ConfigureServices(services =>
{
    services.Configure<HostOptions>(options =>
    {
        options.ShutdownTimeout = TimeSpan.FromSeconds(60);
    });
});
```
